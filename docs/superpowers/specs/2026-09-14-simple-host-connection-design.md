# PC·모바일 간편 연결 — 검토용 설계

상태: 사용자 승인 후 구현 중. QR·초대 링크·저장 호스트를 추가했으며 자동 검증과 배포 결과는 연결된 구현 계획 및 테스트 기록을 따른다.

## 목표와 사용자 흐름

긴 호스트 주소와 티켓을 각각 옮기는 과정을 한 번의 초대 가져오기로 바꾼다.
사용자는 PC와 모바일 모두에서 접속할 예정이다.

1. 회사 PC의 연결된 호스트 화면에 **다른 기기 연결**을 둔다.
2. 호스트 이름을 **회사 PC** 등으로 정하고 **초대 만들기**를 누른다.
3. 같은 초대를 QR과 **초대 링크 복사**로 보여 준다. 유효 시간은 기존 정책인
   5분이고, 한 기기를 등록하면 소비된다. 다른 기기는 새 초대를 만든다.
4. 모바일은 QR을 스캔해 HTTPS 웹 화면을 연다. PC 앱은 **초대 링크 붙여넣기**를
   누른다. PC 브라우저에서는 링크를 바로 열 수도 있다.
5. 호스트 이름·주소가 자동으로 채워지고 기기 이름과 등록 권한을 확인한다.
   사용자가 **이 기기 연결**을 눌러 기존 페어링을 완료한다.
6. 성공한 호스트를 별칭과 함께 저장한다. 다음 접속부터 PC는 저장된 호스트를
   고르고, 모바일은 해당 호스트의 북마크/PWA를 연다. 주소 수동 입력도 유지한다.

## 선택한 방식과 대안

- 선택: QR + 초대 링크 + 별칭 저장. PC·모바일을 함께 지원하고 기존 인증을 재사용한다.
- 대안: Tailscale 기기 이름 변경. 주소 일부만 짧아지고 기존 인증서/Serve 소유 기록에
  영향이 있어 이번 변경에서는 사용하지 않는다.
- 대안: 짧은 숫자 코드 입력. 서로 주소를 모르는 두 기기를 연결할 중개 또는 검색
  기능이 필요해 별도 작업으로 남긴다. 이번 변경에 새 중앙 서버는 추가하지 않는다.

## 구현 경계

현재 App.svelte의 주소/티켓 필드와 AgentApi.pair(), IndexedDB 기기 키 저장소,
인증된 POST /api/v1/pair-tickets의 기존 300초 일회용 티켓을 재사용한다.
호스트 주소는 사용자가 입력한 값이 아니라 실행 중인 Agent가 검증한 public_origin을
사용한다. HTTPS 준비 또는 Agent 재시작이 끝나지 않았으면 초대 생성을 막고 안내한다.

초대는 버전, 정규화된 HTTPS origin, 표시용 별칭, 티켓을 담는다. 비밀인 티켓은
URL query가 아닌 fragment에만 넣고, 수신 즉시 브라우저 주소창에서는 제거한다.
로그·localStorage·저장 호스트 목록에는 티켓을 기록하지 않는다. QR은 로컬에서
생성하며 외부 QR 생성 서비스로 전송하지 않는다. 이름과 origin만 별도로 저장하고
기존 기기 키 저장소 및 만료된 티켓 처리 방식은 유지한다.

PC 앱의 가져오기는 길이 제한, 스키마 버전, HTTPS ts.net 호스트, 기본 443,
사용자 정보/잘못된 URL 요소 부재를 검증한다. 웹 수신은 현재 origin과 초대 origin이
일치해야 한다. 초대 열기만으로 API 요청·권한 부여를 자동 실행하지 않는다.
사용자가 대상과 기기 이름을 확인하고 등록을 눌러야 한다. 티켓은 기존 권한
검증을 거치며 GUI 권한은 이 기능으로 새로 부여하지 않는다.

## 작은 작업 단위

1. 초대 형식의 파싱/검증/직렬화와 별칭 저장, 오류 테스트.
2. 호스트의 초대 만들기·QR·링크 복사 화면.
3. PC 가져오기·모바일 URL 수신·등록·저장된 호스트 선택 화면.
4. M3 결과 리뷰, 자동 테스트, Windows EXE 빌드 및 현재 PC 적용.

코딩은 M3에 관련 파일 1~3개씩 맡긴다. 인증·티켓 경계는 GPT 상위 모델이 검토하고,
반복 실패 시 기존 토큰 고려 정책에 따라 Luna 또는 사용 가능한 Spark로 전환한다.

## 완료 기준

주소와 티켓의 별도 입력 없이 PC 붙여넣기와 모바일 URL 수신이 동작한다.
정상 등록·이미 사용한 티켓·만료·변조 URL·다른 origin·Tailscale 미연결을 구분한다.
기존 수동 입력과 기기 승인 철회는 유지되고, 저장된 별칭으로 재연결할 수 있다.
실제 다른 PC와 모바일 검증은 자동 브라우저 테스트와 별도로 결과를 보고한다.
